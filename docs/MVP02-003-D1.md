# MinePRO AI · MVP02-003-D1

Infraestrutura simulada da especificação homologada em 19/11/2026 pelo termo `MINEPRO-D0-HOM-001`, versão `MVP02-003-D0 v1.2-H1-R1`. A referência do código é o commit `38a818546816c11b7fd345afe44978b98cf9d02b`. [PR #34](https://github.com/Pedrooca4/redpro/pull/34)

## Endpoint conversacional

`POST /api/assistant/conversation` opera atrás de um opt-in explícito, `MINEPRO_D1_MOCK=1`, com Node.js em desenvolvimento ou teste. Use o servidor de desenvolvimento vinculado à interface de loopback. O handler verifica URL, cabeçalhos de origem e indicadores de execução hospedada. Um ambiente de produção ou Vercel responde `UNAVAILABLE/FEATURE_DISABLED` para um pedido válido, mesmo se receber a opção de ativação. O handler da aplicação inicializa o orçamento em **zero micros de dólar**. O orçamento virtual positivo é injetado pelo código de teste e pela matriz.

O primeiro POST válido em desenvolvimento emite um cookie de sessão `HttpOnly` e `SameSite=Strict` e retorna `UNAVAILABLE/SESSION_REQUIRED`. Reenvie o mesmo corpo com o cookie recebido. A sessão é assinada pelo processo local e as chaves são isoladas por sessão e turno. Ao reiniciar o servidor Next.js de desenvolvimento, inicie uma nova sessão. Os testes de reinicialização da lógica financeira restauram o armazenamento sintético e o mesmo principal fictício em separado.

```json
{
  "turnId": "floor-01",
  "idempotencyKey": "floor-01",
  "message": "Quantos blocos preciso para construir o piso da base 21 × 21?",
  "context": { "edition": "JAVA", "game_version": "1.21.1", "mode": "BUILDER" },
  "history": []
}
```

O corpo aceita até 32 KiB, com até 4.000 unidades UTF-16 na mensagem. `history` é opcional e recebe até seis IDs de turnos concluídos da mesma sessão, em ordem cronológica. O servidor obtém o texto e o contexto de cada turno a partir destes IDs. Um seguimento determinístico só passa para o próximo turno se edição, versão e modo coincidirem. Alterar a mensagem, a chave ou o contexto de um turno já registrado gera `IDEMPOTENCY_CONFLICT`. Usar o mesmo ID numa sessão diferente cria um turno independente.

Respostas JSON usam `contractVersion: "1.0"`, `requestId` gerado no servidor e `Cache-Control: private, no-store`. O cabeçalho `X-Request-Id` corresponde ao envelope. Um resultado válido inclui `turnId` e `context`. Um `ERROR` anterior à validação omite esses campos e carrega apenas o código, a mensagem pública e o indicador de nova tentativa.

| Estado          | Origem e evidência                                                                                                                                                                                                                 |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VERIFIED`      | Motor guiado, procedimento compatível e evidência `DOCUMENTED` ou `CALCULATED`. O cálculo do piso registra entradas, fórmula, premissa de uma camada e 441 blocos exatos. A reserva para paredes é estimada e tem fórmula própria. |
| `HYPOTHESIS`    | Fixture fechado selecionado pelo simulador e identificado como ficção. As fontes são vazias e as limitações acompanham o texto.                                                                                                    |
| `CLARIFICATION` | Conflito ou falta de contexto, pergunta do catálogo ou fixture do simulador identificado como tal.                                                                                                                                 |
| `UNAVAILABLE`   | Motivo tipado, incluindo rota desativada, falta de provedor, evidência, orçamento, sessão, tentativa pendente ou incerta.                                                                                                          |
| `ERROR`         | Entrada, capacidade ou falha técnica com mensagem pública controlada e sem stack trace.                                                                                                                                            |

| HTTP | Significado                                                               |
| ---- | ------------------------------------------------------------------------- |
| 200  | Resultado de negócio válido                                               |
| 400  | JSON ou contrato inválido, histórico inválido ou conflito de idempotência |
| 413  | Corpo acima do limite                                                     |
| 415  | Content-Type incompatível                                                 |
| 429  | Capacidade local de 256 turnos atingida                                   |
| 502  | Resposta do simulador rejeitada                                           |
| 503  | Erro interno ou de transporte ou cancelamento                             |
| 504  | Timeout após envio                                                        |

O roteador reutiliza a detecção de conflitos, a validação de resposta e o catálogo do assistente guiado. Esta etapa abrange Java 1.21.1 e Bedrock 1.21.0. Para procedimentos incompatíveis ou pedidos que dependem de dados verificáveis indisponíveis, o serviço devolve uma limitação. Para pedidos conceituais selecionados, o adaptador fictício escolhe um dos fixtures do servidor. Nenhum texto bruto, marcação de verificação ou referência do adaptador passa ao cliente. A resposta é enviada somente depois da validação completa. O chat continua usando `POST /api/assistant`.

## Simulação financeira

A tabela `D1-virtual-v1` usa micros de dólar, com dois micros por byte UTF-8 da entrada completa e cinco por unidade sintética de saída. A reserva inclui toda a entrada e um máximo de 128 unidades de saída. A aplicação padroniza a origem dessa medição e a separa de quaisquer tokens ou custos reais.

Cada tentativa guarda a reserva, a cobrança confirmada quando disponível, a versão de preços e o histórico de transições. A reserva e a deduplicação ocorrem na mesma transação. A intenção de envio é registrada em outra transação antes da invocação. Uma repetição durante o processamento retorna o estado existente. Uma resposta validada gravada antes de uma falha de entrega pode ser recuperada sem repetir o envio.

A restauração de um snapshot num simulador reiniciado libera uma reserva sem intenção e mantém o compromisso de uma tentativa com intenção como `UNCERTAIN`. Uma conciliação exige evidência sintética explícita. A cobrança acima da reserva permanece em `DISPUTED`, contabiliza o maior valor confirmado e bloqueia novas reservas e autorizações até revisão. A revisão preserva os eventos anteriores. O handler HTTP não oferece operação de conciliação.

O armazenamento transacional compartilha estado entre serviços **no mesmo processo**. Snapshots em memória servem aos testes de reinicialização e contêm somente os dados de teste usados na simulação. Para recuperação, os testes param o executor original antes de reabrir o snapshot. A durabilidade distribuída permanece por validar. O armazenamento da rota local e a assinatura de sessão são descartados com o processo.

## Reprodução

No worktree D1 com as dependências da base já disponíveis:

```sh
corepack pnpm check:env
corepack pnpm format:check
corepack pnpm lint
corepack pnpm typecheck
corepack pnpm test
node --experimental-strip-types scripts/evaluate-minepro-d1.ts > /tmp/minepro-d1-matriz.json
NEXT_TELEMETRY_DISABLED=1 MINEPRO_D1_MOCK=1 corepack pnpm dev --port 3141
```

Com o servidor local ativo:

```sh
node scripts/smoke-minepro-d1.mjs enabled http://127.0.0.1:3141
```

A matriz contém 36 conversas com 42 turnos. Dezoito conversas usam o simulador, com 24 invocações e cobertura de Java e Bedrock em cada modo. O JSON registra o SHA-256 do manifesto, as rotas esperadas e executadas, métricas híbridas e do simulador, custos virtuais e percentis com penalidade mínima de 30.000 ms para timeouts. A rubrica exige avaliações independentes. A execução padrão verifica o contrato e a disponibilidade da amostra, e deixa o parecer de qualidade como `INCONCLUSIVE` na ausência de notas. O manifesto é candidato ao congelamento antes de D2.

`pnpm test` também executa os testes de contrato HTTP com orçamento fictício injetado, idempotência, disputa, bloqueio de concorrência, timeout, cancelamento, transporte, reconciliação e recuperação. Esses cenários são independentes da matriz nominal.
