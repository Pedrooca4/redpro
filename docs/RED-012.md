# RED-012 — Query layer e migrações

Backlog: P0, M, depende de RED-011. Aceite: “Criar/aplicar/reverter migração em dev.”

Kysely e pg foram escolhidos conforme a arquitetura permite, com versões fixadas, justificativa no ADR-002 e entrada exclusiva de servidor. O gerador cria arquivos locais de migração; o runner oferece status somente de leitura e aplicação/reversão de uma migração com confirmação explícita de destino e nome.

Após conexão comprovada e autorização de alteração, a migração técnica foi criada, aplicada e revertida no projeto de desenvolvimento. As consultas independentes confirmaram tabela vazia, RLS, ausência de acesso público e remoção da demonstração após rollback. O ledger técnico privado permanece, sem migrações aplicadas. `public`, `auth`, `storage` e dados de produção não foram alterados.

A suíte de integração da CI usa somente PostgreSQL descartável em loopback. O job existente de qualidade/build/smoke foi preservado. Nenhuma migração é executada automaticamente na Vercel, no Supabase remoto ou durante build.

Validação local: 46 testes unitários, formatação, lint, TypeScript, build e smoke HTTP passaram. O ciclo real autorizado no Supabase comprovou o critério de aceite. O novo job de integração PostgreSQL descartável ainda depende de execução real no GitHub após o envio autorizado; não foi apresentado como aprovado antes disso.

Ver [DATABASE.md](DATABASE.md) para comandos, estrutura, limitações e reprodução.
