## Modelo implementado e decisões adicionais

| Objeto        | Contrato                                                                                                                                                                                                                                                                                                                                                        |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| conversations | UUID v4 aleatório com default PostgreSQL; owner_id obrigatório → profiles(id), ON DELETE RESTRICT; title obrigatório 1–160 caracteres sem espaços nas extremidades; edition JAVA/BEDROCK; version opcional/null com 1–64 caracteres alfanuméricos, ponto, hífen, sublinhado ou `+`; default_mode nos seis modos oficiais; created_at/updated_at timestamptz(3). |
| messages      | UUID v4 aleatório; conversation_id obrigatório → conversations(id), ON DELETE RESTRICT; role user/assistant/system/tool; sequence inteiro positivo obrigatório; content textual não vazio até 262144 bytes; selected_mode nos seis modos; tool_refs uuid[] sem nulos, unidimensional, até 32 IDs; created_at/updated_at timestamptz(3).                         |
| Índices       | PK de cada tabela; UNIQUE(conversation_id, sequence), que atende leitura ordenada e FK; conversations(owner_id, updated_at DESC, id), que atende ownership/listagem e FK de proprietário. Sem índices redundantes.                                                                                                                                              |

Limites de título, versão, tamanho de conteúdo, referências e quatro papéis são decisões deste lote, não números impostos pelos documentos. Não há enum SQL global ou dependência nova. Version admite snapshots/pré-releases como 24w12a/1.21-pre1, sem afirmar que a versão existe. IDs próprios têm CHECK v4; IDs de Auth continuam externos e sem imposição de versão. Tipos Kysely reutilizam RED-023 e os tipos Edition/Mode existentes por import **somente de tipo**, sem levar banco à UI.

`sequence` começa em 1; unicidade é por conversa, não global. Lacunas são permitidas e a ordem deve ser explícita em SELECT/ORDER BY. Não usar UUID/data como posição. Não há default, contador, max()+1 ou alocador concorrente nesta tarefa de schema. O backend futuro deve serializar/alocar posições em transação e tratar disputa/erro de unicidade; isso não está implementado por estes tipos ou índices.

`tool_refs` referencia IDs futuros de execuções, sem criar tool_executions antecipadamente. Não há FK para entidade inexistente nem garantia de existência/procedência. Antes de usar referências reais, adicionar o vínculo/validação em lote autorizado. Referências nunca significam que uma ferramenta foi executada ou que o conteúdo foi validado.

Conteúdo protegido significa **privacidade por grants/RLS**, não criptografia ponta a ponta ou criptografia de campo. Não é renderizado, logado, exposto por API nem enviado a modelo neste lote. Texto é dado não confiável; sanitização/minimização de logs e renderização segura pertencem aos futuros endpoints/UI. Não guardar credenciais ou logs pessoais brutos. Este schema não define consentimento, retenção, backups ou apagamento completo.

## Segurança e papéis

As duas tabelas têm ENABLE + FORCE RLS explícitos. A migração revoga defaults amplos **apenas nestas tabelas novas**, sem alterar default privileges, profiles, Auth, public.rls_auto_enable() ou ensure_rls.

| Papel               | Conversas                                                                                                                                                                                                                | Mensagens                                                                                                                                   |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| PUBLIC / anon       | Nenhum grant                                                                                                                                                                                                             | Nenhum grant                                                                                                                                |
| authenticated       | SELECT próprio; INSERT apenas owner_id/title/edition/version/default_mode com WITH CHECK próprio; UPDATE apenas contexto/título, USING e WITH CHECK próprios. Sem DELETE/TRUNCATE ou escrita em ID/ownership/timestamps. | SELECT apenas quando a conversa pertence a auth.uid(); sem INSERT/UPDATE/DELETE/TRUNCATE, inclusive para mensagens de papel user.           |
| service_role        | Somente SELECT, acesso privilegiado do backend                                                                                                                                                                           | SELECT e INSERT apenas conversation_id/role/sequence/content/selected_mode/tool_refs; sem escrita em ID/timestamps, UPDATE/DELETE/TRUNCATE. |
| Dono administrativo | Privilegiado; não é sessão de jogador                                                                                                                                                                                    | Privilegiado; não deve ser conexão de futuras rotas públicas                                                                                |

Há três políticas de conversa e uma de leitura de mensagens, com ownership explícito e `(SELECT auth.uid())`. Sessão sem UID não vê linhas; RLS do pai também limita o EXISTS usado por mensagens. Não confiar em role, owner_id, conversation_id ou posição recebidos do navegador. O backend futuro precisa verificar sessão e ownership **antes de usar service_role**, definir role/sequence por código confiável e tratar o texto do usuário como dados. Uma chave service_role tem BYPASSRLS e deve ficar privada; não há autenticação/API criada aqui nem garantia de segurança de endpoint ainda inexistente.

Mensagens ficam somente leitura para clientes intencionalmente: até mensagens de papel user devem passar pelo backend autorizado, impedindo falsificação de assistant/system/tool e posição arbitrária. O contrato de armazenamento TypeScript aceita papéis do backend; não representa permissão de cliente. service_role não recebe acesso adicional a profiles nem pode criar/alterar conversas por estes grants.

O schema privado `minepro_chat_internal` contém duas funções SECURITY INVOKER com search_path pg_catalog, sem grants de schema/EXECUTE para os papéis de API. Triggers BEFORE UPDATE rejeitam mudanças em IDs, ownership/conversation_id, role, sequence e created_at, inclusive por SQL administrativo. Atualizações autorizadas recebem updated_at de statement_timestamp(), sem relógio de cliente, consistente com RED-023 e com avanços dentro da mesma transação. A atualização de uma mensagem não altera automaticamente a data da conversa: um futuro fluxo composto deve atualizar a conversa explicitamente. Nenhuma função SECURITY DEFINER nova.

## Migração, ordem e reversão

Gerada pelo `scripts/db-new.mjs` existente: `20261030153608225_conversations_messages.ts`, com SQL up/down congelado. O wrapper não importa schema mutável da aplicação. O runner exige destino/fingerprint/nome, mantém lock/ledger e executa uma migração por comando. Build/deploy não aplicam SQL.

Ordem obrigatória: development_probe → profiles → conversations_messages. Up exige RED-013 identificado, PK UUID, auth.uid() UUID, permissões de sessão e papéis existentes com authenticated sem BYPASSRLS e service_role com BYPASSRLS. Não cria/repara esses pré-requisitos. Colisões falham sem IF NOT EXISTS/adotar objetos. Aplicar SQL solto e marcar o ledger manualmente não faz parte do procedimento.

Down, na transação do runner: trava as duas tabelas; row_security=off impede interpretar linhas invisíveis como tabela vazia; exige comentários de identidade e ambas vazias; remove filho antes do pai e somente os objetos deste lote, **sem CASCADE**. Dados/dependências/objetos alheios causam recusa e rollback transacional. Nunca limpar tabelas reais para forçar reversão. Reversão real exige autorização específica. ON DELETE RESTRICT mantém o perfil e a conversa enquanto existirem dependentes; a futura exclusão de conta precisa de fluxo explícito de retenção/remoção, inclusive Auth → perfil → conversa → mensagem.
