## Convenções implementadas

- Registros próprios: PostgreSQL `uuid`, PK com `DEFAULT gen_random_uuid()`; UUID v4 aleatório, sem sequência pública. Backend pode usar `newRecordId()` quando precisar do ID antes do INSERT. `parseRecordId()` valida versão/variante e formato com hífens, normaliza para minúsculas, rejeita entradas sem ecoá-las em erros. Um ID imprevisível não substitui autorização.
- Identidades externas, como o futuro vínculo com Supabase Auth, preservam o ID do provedor; não gerar um segundo usuário com `newRecordId()`. O contrato do provedor será validado na RED-013.
- Instantes: `created_at` e `updated_at`, `timestamptz(3) NOT NULL DEFAULT now()`. Precisão de milissegundos coincide com `Date`/pg e JSON. Ambos começam no mesmo instante da transação.
- Pool SQL inicia sessões em UTC. `timestamptz` representa o instante independentemente do fuso da sessão; não preserva o fuso original. O backend serializa `Date` finito como ISO 8601 UTC com `Z`, usando `toUtcTimestamp()`. Anos aceitos: 0001–9999. A função não recebe strings nem descobre o fuso de um `Date` já construído: futuras entradas textuais exigirão validação de formato, calendário e offset explícito na fronteira da API.
- Atualizações: data access futuro deve incluir `updated_at: updatedAt()` **na mesma instrução UPDATE**. Usa `statement_timestamp()`, que avança entre instruções dentro da mesma transação. `created_at` e ID são imutáveis no contrato Kysely. Não há gatilho automático: escritores SQL externos também terão de seguir a política. Antes de permitir esses escritores, revisar se um trigger será necessário em tarefa própria.
- Datas civis futuras, sem instante, usam `date` e representação `YYYY-MM-DD`, sem conversão por UTC. Não há campo de data civil nesta entrega, portanto não foi criado parser adicional.
- Ordem de mensagens futura usa `sequence` com unicidade por conversa; UUID e timestamps não são contadores, relógios monotônicos nem critério suficiente de ordenação total.

`src/db/index.ts` mantém a entrada `server-only`. O módulo de política importa `node:crypto` e não deve entrar na UI. `RecordColumns` impede alterações tipadas em ID/criação e timestamps arbitrários em INSERT; TypeScript não é controle de acesso nem proteção contra SQL bruto.

## Modelo para as próximas migrações

As migrações futuras devem congelar explicitamente as definições, sem importar helpers mutáveis da aplicação:

```sql
id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
created_at timestamptz(3) NOT NULL DEFAULT now(),
updated_at timestamptz(3) NOT NULL DEFAULT now()
```

O fixture descartável testa esse SQL com Kysely/pg, sem criar tabelas de perfis ou conversas. Migrações históricas não foram alteradas. Não é necessário instalar extensão para `gen_random_uuid()` no PostgreSQL 17.

## Validação

- Unitários: geração/validação de UUID, entradas inválidas, offset negativo e fracionário, virada de dia, ano bissexto, datas inválidas e erros sem conteúdo de entrada.
- Contrato compilado: defaults opcionais, ID validado, criação imutável, relógio do banco em updates e retorno pg como Date.
- Integração: apenas `local-test`/ambiente `test`, tabela temporária `ON COMMIT DROP`, UUID gerado no PostgreSQL, duplicidade com savepoint, timestamps iniciais iguais, UPDATE na mesma transação, criação preservada e roundtrip UTC/São Paulo/offset explícito.
- `test:db` inclui todos os arquivos `tests/integration/*.test.ts`; preserva integralmente o teste de migrações anterior e o serviço descartável da CI, sem secrets Supabase.
