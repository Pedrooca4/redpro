## Tabela e contratos

| Campo                   | Contrato                                                                                                                                                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| id                      | uuid, PK e FK para **auth.users(id)**; obrigatório, sem default/gerador. Preserva o ID externo, inclusive UUID de versão diferente de v4. ON DELETE RESTRICT evita remoção silenciosa do perfil ao excluir a identidade. |
| display_name            | text obrigatório; 1–80 caracteres e sem espaços comuns nas extremidades, por CHECK. Limite 80 é decisão de implementação deste lote, não uma exigência literal do backlog. Não é login nem identificador único.          |
| preferences             | jsonb obrigatório, objeto JSON, default `{}`. Privado; nenhum campo de privilégio/role é usado para autorização.                                                                                                         |
| created_at / updated_at | timestamptz(3), obrigatórios, default now(); consistentes com a precisão e o pool UTC da RED-023.                                                                                                                        |

A PK já fornece índice para FK, ownership e lookup por usuário; não há índice redundante ou listagem pública. Contrato ProfilesTable integrado ao Database Kysely e exportado pela entrada server-only. Tipos reutilizam os timestamps da RED-023. parseAuthUserId valida sintaxe UUID e normaliza letras; só a FK comprova existência no Auth. Não chamar newRecordId para perfis. A inclusão de tipos não afirma que uma tabela existe no ambiente.

O SQL só consulta os pré-requisitos gerenciados de Auth e exige PK UUID em auth.users(id), auth.uid() retornando UUID e permissões de sessão já existentes. Não cria/repara objetos Auth nem grants de Auth. Sem esses contratos, falha antes de materializar perfis.

## RLS e privilégios mínimos

ENABLE e FORCE ROW LEVEL SECURITY explícitos, sem depender de public.rls_auto_enable ou ensure_rls. Nenhuma modificação nesses dois objetos.

- SELECT: apenas authenticated, com `(SELECT auth.uid()) = id`.
- INSERT: WITH CHECK do mesmo proprietário; somente colunas id/display_name/preferences.
- UPDATE: USING e WITH CHECK do mesmo proprietário; somente display_name/preferences.
- Sem grant/policy DELETE, acesso anon, perfil público ou acesso da role service_role. Grants amplos que possam vir dos defaults Supabase são revogados **somente na tabela nova**; default privileges não são alterados.
- Papel sem UID recebe zero linhas e não consegue criar perfil. Não basta pertencer a authenticated: a identidade precisa coincidir.

Novo schema privado **minepro_profile_internal** contém apenas stamp_profile_update(), função SECURITY INVOKER com search_path=pg_catalog, sem elevação de direitos e sem grants de uso/execução para os papéis de API. Um trigger BEFORE UPDATE em profiles preserva id/created_at e atribui updated_at por statement_timestamp() com precisão de milissegundos. O mecanismo de trigger deve funcionar sem permitir chamada direta ao helper; isso está exigido no teste descartável.

Essa extensão específica para profiles é necessária porque clientes authenticated recebem UPDATE apenas de nome/preferências: não recebem permissão para fornecer o relógio. O helper SQL updatedAt() da RED-023 continua válido para escritores de backend autorizados e não foi alterado. Não há obrigação de um writer lembrar de atualizar o relógio desta tabela. Isso não implementa autenticação.

Administradores com BYPASSRLS/superuser continuam privilegiados; FORCE RLS não os transforma em usuários finais. A conexão administrativa atual é exclusiva de ferramentas, nunca um substituto de sessão para futuras APIs. A simulação de claim nos testes não valida JWT, não implementa login e não autoriza confiar em dados enviados pelo cliente.

## Migração e reversão

Arquivos `20261029222313139_profiles.up.sql` / `.down.sql`, carregados pelo wrapper Kysely `.ts` do mesmo nome. Criados pelo gerador de migrações existente; SQL congelado e sem imports do schema de aplicação. Provider reconhece o wrapper e ignora os arquivos .sql; scripts de migração e suas proteções de destino continuam existentes. Não há migração no build/deploy.

Executar somente dentro da transação do runner Kysely. Up recusa colisões, sem IF NOT EXISTS. Down bloqueia a tabela, exige marcas de identidade e tabela vazia, usa row_security=off para recusar uma contagem filtrada por RLS, e remove somente os objetos próprios sem CASCADE. Dependências/objetos alheios impedem o drop, com rollback da transação. Nunca excluir linhas para “forçar” rollback em banco real. O workflow de exclusão de conta/retenção é futuro: RESTRICT bloqueia exclusão do Auth enquanto existir perfil; a escolha precisa ser revisada antes de implementar esse fluxo.

Antes de aplicação real: revisar SQL e grants herdados no destino, verificar estado/ordem pelo runner, compatibilidade de Auth e Data API, autorizar cada migração e conferir catálogo/RLS depois. Não saltar migrações anteriores pendentes. Rollback real requer autorização própria e avaliação dos dados existentes. Não copiar valores das variáveis Vercel de origem distinta.
